# Illustrated daily recap

Use after the dated evidence and report facts are reconciled. The owner requests actual image generation for the infographic, not a screenshot, HTML chart, scatterplot, or a decorative rendering of the report table. Use the host's image-generation capability and relevant image skill. If unavailable, deliver the factual text report and state that the image could not be generated; do not silently substitute an unrelated visual format.

## Always deliver English and Arabic

End each report with two separate generated infographics, English first and Arabic second, using the same factual manifest, achievements, date, timestamps and metrics. This is the default for every invocation, regardless of the written report's language; do not ask the user to pick one. An explicit current request for text only or a single language overrides the default. If generation is unavailable or one version fails, say exactly which output is missing rather than claiming both were delivered.

Use natural Arabic, correctly shaped readable type and right-to-left hierarchy; preserve Western digits (0–9) and keep Latin identifiers, times and version numbers legible. Localize labels and explanatory notes without changing counts or completion status. Preserve the approved illustration, color hierarchy and visual structure across the two languages, adapting spacing and reading order as needed.

Both images show achieved outcomes and delivered progress only. Exclude unfinished work, blockers, next actions and any “still open”/“لم يكتمل بعد” section or banner. Keep those facts in the written report. This does not permit hiding a reversal or calling unfinished work complete: omit a misleading highlight or qualify the delivered portion. Retain concise source/metric qualifications needed to interpret the achievements and numbers honestly.

## Visual idea: make parallel work visible

Show one person's day branching into distinct projects/work streams, with concrete outputs moving through research, creation, revision and publication. Let the composition imply multiplied capability through parallel lanes, branches or small illustrated work scenes converging into delivered results. Do not literally write “superhuman,” claim impossible abilities, invent extra projects or add a fictional productivity multiplier/hours-saved claim.

Use actual distinct projects when several are evidenced. If the day has one business with analytics, social, website and video work, show one project with four labeled work streams. Never label four chats or two folders as four projects. With verified overlapping turn intervals, illustrate overlap; otherwise use parallel thematic lanes without claiming all tasks ran simultaneously or measuring continuous work time.

Favor immediate readability: large modern sans-serif text, short labels, ample whitespace, restrained background/palette and a few informative illustrations. Avoid busy props, tiny footnotes, walls of text, excessive badges, and a generic dashboard. Read [the brand style](brand-style.md) before generation. Use yellow `#FFE04A`, cream `#FAF8F2` and ink `#15130F`: cream canvas, ink typography, yellow emphasis and warm neutral panels, one central operator with an AI hub branching into illustrated outputs, and a prominent bottom metrics strip. Carry the palette through illustrations; preserve the approved composition. This supersedes earlier navy/purple/pastel examples. Adapt the project/panel count to the day rather than hard-coding four workstreams.

## Preserve the actual work, not only its last action

Important deliverables should show their major stages: researched → designed/edited → revised/tested → published, where the evidence supports them. Do not compress hours of video revisions into “shipped a video,” or a new product into “deployed.” Distinguish creating something new from revising an existing asset. Do not count a proposed idea as implementation or a scheduled post as already published.

Use a small number of meaningful timestamps, exact known output counts and plain status labels. Exclude pending items from the images; describe them only in the written report. The image is a highlights companion, not proof that every action in the underlying report is pictured.

## Scale strip at the end

Add a readable end-of-day scale strip with verified project count, conversation-message count, and recorded tokens where available. Show distinct chat/work-stream counts separately when useful. The strip must use exact definitions and coverage from the report; it is not a productivity score.

- **Projects:** semantic product/business grouping established by reading the chats, with a small mapping in the report. Count worktrees/chats/shared media workspaces within the same project once. If uncertain, state the number of workspaces and leave project count unavailable pending clarification.
- **Messages:** deduplicated visible conversation messages, with user-side/assistant breakdown in the report. Include commentary if using the collector's default; disclose automation/handoff entries. Do not count tool calls, system text, model reasoning or repeated fork context as messages. Count support-agent exchanges separately if included.
- **Tokens:** per-response recorded usage, deduplicated by response ID inside the local-date window. Label “recorded tokens” and disclose cached input/context processing. Do not add cumulative counters, cached-input subsets or reasoning subsets again. Do not infer tokens from character length, use lifetime totals as daily usage, convert to cost, or fabricate usage for remote sources without it. Use “not available” or clearly scoped partial coverage if necessary.

Token volume is a processing measure, not unique writing, useful output or quality. Huge cached-context counts need an explicit label; do not market them as billions of new words. Counts must use the same source scope and date as the report. Unavailable metrics should be omitted or marked unavailable, never replaced with plausible guesses.

## Generation and review

Build an exact factual text manifest first, including selected achieved milestones, delivered stages/status, project grouping and metric definitions. Keep pending work in the written report and out of the image manifest. Give that manifest to image generation with a readability-focused composition brief. No private customer details, credentials or raw chat exports belong in the image.

Inspect the generated image: every displayed number/date/time, label, status and project count must match the manifest. Check readability and ensure the design preserves the work stages and distinguishes scheduled/published and reported/verified. Correct wrong labels with a targeted edit before delivery. Show both actual generated images at the end of the report, labeled English and العربية. Check both versions independently for text accuracy, then compare their facts, numbers, dates and status labels. The current illustrated direction is approved; apply it without another style-approval step unless the user requests a new direction.
